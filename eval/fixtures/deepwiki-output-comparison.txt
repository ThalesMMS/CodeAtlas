Tinycommerce is built using a decoupled architecture consisting of a **Go backend** and a **TypeScript frontend**. The system follows a strict layered pattern on both sides to ensure maintainability and testability. The backend implements a classic three-layer pattern (Handler, Service, Repository), while the frontend utilizes a two-layer controller/client pattern.

## System Communication

The frontend and backend communicate exclusively over HTTP using JSON payloads. The frontend acts as a consumer of the backend's REST-like API.

1.  **Transport**: The frontend uses the browser `fetch` API to send `POST` requests [web/src/api.ts:8-16](web/src/api.ts#L8-L16).
2.  **Serialization**: Data is serialized from TypeScript camelCase objects into Go-compatible PascalCase JSON [web/src/api.ts:11-15](web/src/api.ts#L11-L15).
3.  **Routing**: The Go backend uses `http.ServeMux` to route requests to specific handlers [cmd/api/main.go:15-16](cmd/api/main.go#L15-L16).

The Go backend is organized into three distinct layers, wired together via Dependency Injection (DI) during application startup in `main.go`.

## Frontend: The Two-Layer Pattern

The TypeScript frontend separates business logic and validation from the technical details of network communication.

### 1. Controller Layer
The `CheckoutController` acts as the entry point for frontend actions. It performs client-side validation using `validateCheckout` before attempting any network calls [web/src/checkout.ts:3-15](web/src/checkout.ts#L3-L15). This prevents unnecessary server load for obviously malformed data.

### 2. API Client Layer
The `api.ts` module encapsulates the `fetch` logic. It is responsible for:
*   Mapping the internal `OrderInput` interface [web/src/api.ts:1-5](web/src/api.ts#L1-L5) to the JSON structure expected by the Go backend (e.g., mapping `id` to `ID`).
*   Handling non-OK HTTP responses by parsing the error text and throwing an exception [web/src/api.ts:18-20](web/src/api.ts#L18-L20).

## Error Handling and Status Codes

The architecture uses standard HTTP status codes to communicate the result of operations back to the frontend:

*   **201 Created**: The order was successfully validated and saved [internal/order/http.go:26](internal/order/http.go#L26).
*   **400 Bad Request**: The JSON payload was syntactically malformed [internal/order/http.go:19](internal/order/http.go#L19).

The Domain Model represents the core business logic and data structures of the `tinycommerce` system. In this architecture, the domain model is intentionally lean, focusing on the `Order` aggregate which serves as the primary unit of data transfer and persistence across the backend layers.

## The Order Aggregate

The `Order` struct is the central entity defined in the `order` package. It encapsulates all necessary information required to process a checkout transaction.

### Field Definitions

| Field | Type | Description |
| :--- | :--- | :--- |
| `ID` | `string` | A unique identifier for the order, typically provided by the client or generated during the checkout process. |
| `CustomerID` | `string` | The unique identifier of the customer who placed the order. |
| `TotalCents` | `int64` | The total value of the order represented in the smallest currency unit (cents). |
| `CreatedAt` | `time.Time` | The timestamp indicating when the order was officially recorded in the system. |

### Rationale: Integer-Cent Representation
The `TotalCents` field uses an `int64` type rather than a floating-point number (like `float64`). This is a critical design decision to avoid precision errors inherent in binary floating-point arithmetic when dealing with currency. By using integers to represent the smallest unit of currency (e.g., $1.00 is represented as `100`), the system ensures exact calculations for additions and subtractions across the service and repository layers.

The Repository Layer provides an abstraction for the persistence of order data, decoupling the domain logic from specific storage implementations. It defines a contract for saving and retrieving `Order` aggregates and provides an in-memory implementation for use in development and testing.

## The Repository Interface

The `Repository` interface [internal/order/repository.go:9-12](internal/order/repository.go#L9-L12) defines the persistence contract. By using an interface, the `Service` layer remains agnostic of whether data is stored in volatile memory, a relational database, or a document store.

| `Save` | `(ctx context.Context, order Order) error` | Persists a new or existing `Order`. |
| `Find` | `(ctx context.Context, id string) (Order, bool)` | Retrieves an `Order` by its unique identifier. Returns the order and a boolean indicating if it exists. |

**Sources:**

## MemoryRepository Implementation

The `MemoryRepository` [internal/order/repository.go:14-17](internal/order/repository.go#L14-L17) is the default implementation provided by `tinycommerce`. It stores data in a Go `map` and is designed for thread-safety using synchronization primitives.

### Concurrency Model
Because the Go HTTP server handles requests in concurrent goroutines, the `MemoryRepository` must protect its internal state. It uses a `sync.RWMutex` [internal/order/repository.go:15](internal/order/repository.go#L15) to manage access:
- **`Save`**: Uses `r.mu.Lock()` [internal/order/repository.go:24](internal/order/repository.go#L24) to acquire an exclusive write lock, ensuring that only one goroutine can modify the `orders` map at a time.
- **`Find`**: Uses `r.mu.RLock()` [internal/order/repository.go:31](internal/order/repository.go#L31) to acquire a shared read lock, allowing multiple concurrent readers while blocking any writers.

## Freezing Time via the Clock Field

The `Service` struct contains a `clock` field [internal/order/service.go:12](internal/order/service.go#L12), which is a function returning `time.Time`. By default, this is set to `time.Now` in the constructor [internal/order/service.go:18](internal/order/service.go#L18).

To test logic dependent on the `CreatedAt` field [internal/order/model.go:9](internal/order/model.go#L9), use a test in package `order` (not `order_test`) and override the package-private field:

```go
// Example of freezing time in a test
svc := NewService(repo)
svc.clock = func() time.Time {
    return time.Date(2023, 1, 1, 12, 0, 0, 0, time.UTC)
}
```

This ensures that every `Order` saved via `Submit` [internal/order/service.go:22](internal/order/service.go#L22) has a deterministic timestamp, allowing for exact assertions against the repository.

# Overview

`tinycommerce` is a lightweight, proof-of-concept e-commerce system designed to demonstrate a clean, layered architecture using **Go** for the backend and **TypeScript** for the frontend. The project emphasizes clear separation of concerns, dependency injection, and predictable data flow between the client and server.

The system focuses on the core "Order" domain, providing a pipeline from a web-based checkout interface to a persistent (in-memory) storage backend.

### System Purpose and Scope

The primary goal of `tinycommerce` is to provide a reference implementation for:

* **Layered Go Backend**: Utilizing a Repository-Service-Handler pattern.
* **Typed Frontend**: A TypeScript-driven UI that communicates with a RESTful API.
* **Decoupled Design**: Ensuring the business logic is independent of the delivery mechanism (HTTP) and storage implementation (In-Memory Map).

### High-Level Architecture

The project is split into two distinct environments that communicate over HTTP. The backend is built as a single Go module `example.com/tinycommerce` [go.mod:1-3](go.mod#L1-L3), while the frontend resides in the `web/` directory.

### The Go Backend

The backend is structured to ensure that business rules are isolated from infrastructure. It uses a three-layer pattern initialized in the application entry point [cmd/api/main.go:10-18](cmd/api/main.go#L10-L18).

1. **Repository Layer**: Manages data persistence. The current implementation uses an in-memory map protected by a mutex.
2. **Service Layer**: Contains the core business logic, such as order validation and timestamping.
3. **HTTP Handler**: Acts as the interface to the outside world, translating JSON requests into domain models and handling HTTP status codes.

The server listens on `127.0.0.1:8090` [cmd/api/main.go:17](cmd/api/main.go#L17) and exposes a single endpoint: `POST /orders` [cmd/api/main.go:16](cmd/api/main.go#L16).

For a deep dive into the backend components, see **[Backend: Order Service](2-backend-order-service.md)**.

### The TypeScript Frontend

The frontend is a lightweight TypeScript application that manages the user's checkout state and coordinates with the backend API. It mirrors the backend's discipline by separating UI logic from network communication.

* **Checkout Logic**: Validates the state of the shopping cart before attempting a submission.
* **API Client**: Handles the mapping of frontend camelCase properties to the PascalCase fields expected by the Go JSON decoders.

For details on the frontend implementation, see **[Frontend: Checkout Web App](3-frontend-checkout-web-app.md)**.
